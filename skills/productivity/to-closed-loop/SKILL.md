# to-closed-loop — 广义闭环驱动器

一个交付物从"我做完了"到"证明了做完了"的驱动器。不管选方向（那是 next-step 的事），
不管具体怎么测（那是各验证后端的事），只管三件事：**定义什么算闭环、强制证据、收口**。

## 两条铁律

- **没有标准不动手验证**：先有可判定的验收标准，再谈验证。标准必须是"能回答是/否"的句子。
- **没有证据不下结论**：每条标准要么有证据判绿，要么进剩余风险清单，不允许"应该没问题"。

## 工作流

### Step 1 — 共创验收标准（用户不知道怎么闭环时主推）

先一句话确认交付物与目标（`目标：… ／ 交付物：…`），然后**按交付物类型推荐 2-4 条候选
标准**，用户删改确认。不问"你想怎么验证"——用户答不上来才找的你。

候选标准从两个维度生成：

- **正确性**：核心功能/结论在典型输入下对（如：命令跑通无报错、文档命令逐条可执行、
  评测通过率不回退、配置在真实环境生效）
- **完备性**：边界与副作用（如：清理了过程产物、改 A 没弄坏 B、下游使用者被告知）

每个候选标准带一句"怎么判"（跑什么命令 / 看什么现象 / 问谁）。用户全部答不上"怎么判"
的标准删掉，不许留不可判定的。

`GREEN:` 用户确认了 2-4 条标准，每条都能回答是/否。

### Step 2 — 分诊验证后端

按交付物类型路由，能交给现成后端的交出去：

| 交付物 | 后端 | 说明 |
|---|---|---|
| 代码仓库/网站/CLI | `/verify-run` | 有验收手册照单执行；无手册轻量审计 |
| DeepWorks agent/知识库 | `dp-eval-run` | 问题集回归 + diff；取证用 dp-session-forensics-cloud |
| 流程可重复的验证 | `/verify-replay` | verify-run 全绿后固化为 YAML 回放 |
| 文档/配置/决策/skill/一次性的东西 | 轻量自检（本技能内置） | 逐条标准执行或取证，见下 |

轻量自检的取证规则：标准说"命令跑通"就真跑一遍；说"文档命令可执行"就抽 2-3 条真执行；
说"评测不回退"就调对应 eval。**自检结果附证据**（命令输出摘要/文件路径/截图），不写空话。

### Step 3 — 判定与回修

逐条标准出判定：`✅ 证据：…` / `❌ 证据：…`。

- 全绿 → 进 Step 5
- 有红 → 列出修法（做什么/代价），**问用户修不修**；修完重跑红的那几条（不整轮重跑）。
  连续两轮修不完 → 建议进逼近模式，别死磕。

### Step 4 — 逼近模式（无法 100% 闭环时）

触发：验证环境没有、代价过高（要生产数据/要等真实用户）、或标准本质主观。
此时不硬卡，把闭环度显式化：

```markdown
## 证据链（已证明）
- ✅ 标准1：证据…
- ✅ 标准2：证据…

## 剩余风险（未证明）
- ⚠️ 标准3 无法验证：<原因>；影响：<多大/谁受影响>；补位手段：<上线后盯什么/何时补验>
```

每个未证明项必须有三要素（原因/影响/补位）。**用户看完风险清单拍板**：接受收口，
或补条件继续验。逼近模式不是放弃闭环，是把"没闭环的部分"从暗处搬到明处。

### Step 5 — 收口

全绿或用户接受风险清单后：

1. 输出一行闭环声明：`闭环 ✅（3/3 标准）` 或 `收口 ✅（2/3 标准 + 1 项已确认风险）`
2. 清理过程产物（评测会话/临时文件），该用 cleanup 的用 cleanup
3. 问一句要不要沉淀：本次验收标准值得进 memory / 写进 verify-replay / 留作下次基线吗

## 与近亲技能的分工

- **next-step**：做完/卡住时选**方向**（3-5 个选项）；本技能选完方向后**收口**
- **verify-run 系**：代码场景的验证**后端**；本技能是**前端驱动器**，含标准共创与逼近模式
- **grill-one**：打磨"做什么"；本技能证明"做对了"
