# 通用验证执行器

用 opencli（浏览器）+ curl（API）+ 本地命令（CLI）代替人眼执行验证，产出带证据的验证报告。默认输出到：

`docs/verification/verify-run-report.md`

只有 URL、没有仓库时，报告写到当前工作目录 `verify-run-report.md`。

## 前置检查

执行前先确认 opencli 可用：`opencli doctor`。不可用时提示用户先跑 setup-opencli 技能配置浏览器桥接，不要降级为纯口头验证。

## 输入分档（自动探测，按顺序判定）

### 档① 有验收手册

`docs/verification/manual-test-guide.md`（或用户指定的手册路径）存在时，解析其中的验收项：

- 只执行带结构化操作步骤的验收项（`open / click / fill / upload / curl / run / wait / screenshot` 动词 + `预期:` 行）。
- 「自动检查」章节的命令（pytest / build / typecheck 等）先跑一遍，失败不阻塞后续手动项，但要记入报告。
- 服务未启动时按手册「启动服务」章节启动；手册写明默认不自动启动的，先问用户。
- 断言判定：客观断言（状态码、文本存在、元素出现、跳转目标）直接判定；模糊断言（布局无错位、流程顺畅）用截图 + 自己判读，判读依据写进报告。
- 手册中步骤与实际不符（元素找不到、URL 404）时，记录实际观察，标记 `fail(手册偏差)`，不要卡死重试超过 2 次。

### 档② 有仓库无手册

用户给了项目目录、但没有手册时，做轻量审计现场推导验证步骤，**不生成完整手册、不创建 dev.sh**（那是 verify-manual-after-implementation 的职责）：

1. 快速收集事实：README、package.json / pyproject.toml / Makefile / compose 文件里的启动命令，路由/页面入口，健康检查端点，样例数据，已有的自动化测试命令。
2. 启动服务（能可靠识别才启动；识别不了就问用户怎么启动）。
3. 推导验证点：主路径走通（首页打开、核心 API 200、关键表单提交或核心流程 1-2 条）+ 自动检查命令。验证点数量按用户诉求裁剪——"冒烟一下" 3-5 个点即可，不要自行扩大成全量验收。
4. 把推导出的步骤先列给用户确认（一句话清单），再执行。

### 档③ 只有 URL

用户只给一个网址（常见于验证别人的网站/线上环境）：

1. 不启动任何服务，不碰本地仓库。
2. 和用户确认验证意图：用户说清要验证什么就按用户的来；用户只说"看看能不能用"则默认验证可达性、首页渲染、主要导航/入口可点、无明显报错（控制台错误、5xx）。
3. 探索式驱动 opencli 执行，每个验证点留存截图证据。
4. 注意这是别人的环境：只做只读操作（打开、查看、导航），**不做**注册、提交表单、删除、灌数据等写操作，除非用户明确要求且确认过后果。

## 执行纪律

- 每个验证点独立判定 pass / fail / skip，互不阻塞；一个失败不中断整体。
- 证据先行：pass 也要留最小证据（截图或响应摘录），不能只写"通过"。
- 环境状态变化（启动了服务、修改了数据）记录到报告的「环境变更」小节，验证结束后询问是否回收（停服务、清理测试数据）。
- 验证过程中不要顺手修代码；发现问题只记录，修复是后续动作。

## 报告格式

```markdown
# 验证报告

- 时间：
- 输入档位：①手册 / ②仓库推导 / ③URL 探索
- 环境：（URL / 本地服务、启动方式、关键版本）

## 结果总览

| # | 验证点 | 结果 | 证据 |
| --- | --- | --- | --- |
| 1 | ... | pass | screenshots/01-home.png |
| 2 | ... | fail(手册偏差) | api-response.json |

## 详细记录

（每个非 pass 项：操作步骤、期望、实际观察、证据、初步判断）

## 自动检查

（命令与结果）

## 环境变更

（启动/修改了什么）
```

## 与后续技能衔接

- 报告全绿时，提示用户可用 verify-replay 把本次执行固化为 YAML 回放清单，便于下次快速回归。
- 报告有 fail 时，提示先修复再重跑，不要生成回放清单。
