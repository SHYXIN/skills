# Skill Iterate

打磨一个已存在的 skill。输入是一次真实使用中暴露的摩擦，输出是一个**外科手术式的小步修改**——一次只改一类行为，并同步真相源。

改 skill 和写 skill 是两种工作：写新 skill 见 `writing-for-agents-wx`；本 skill 只管**迭代**。

## 为什么小步

matt/skills、rea、context-mode、book-to-skill 四个高维护 skill 仓库的共同规律：**没有大爆炸式重写，只有长期小步精修**。一次提交只改一两句行为描述（matt 的 grilling 修一次措辞 diff 仅 +2 行），每个改动可溯源到一次真实使用（issue 号），每个改动留变更记录。大爆炸重写摧毁的正是这些小修复积累的行为校准。

## 步骤

### 1. 定位摩擦——先要一手证据

拿到摩擦描述后，先找**发生了什么**的证据，再想怎么改：

- **会话记录**：当前会话直接用上下文；历史会话直接 grep 本机各 harness 的 jsonl 日志（`~/.codebuddy|claude|codex|copilot|pi/...`，窄关键词搜内容、`ls -t` 按时间翻）。找 skill 实际运行时的关键片段：它读了什么、跳过了什么、在哪一步跑偏。
- **没有证据时**，向用户要一个具体实例：「上次它做了什么、你期望什么」。不要基于想象中的失败模式改 skill——那是往 skill 里塞 no-op。
- 摩擦分类（决定改动类型）：
  - **误触发**（不该调用时调用了）→ 收紧 description 的触发措辞
  - **该触发没触发**（该调用时没调用）→ 补触发词/分支，或 description 缺身份信息
  - **抢跑**（步骤没做完就宣称完成）→ 磨锐完成标准，或拆分顺序
  - **粒度不对**（一次讲太多/太少）→ 调整步骤拆分
  - **no-op**（某条指令不改变行为）→ 删除而非重写
  - **纯杂质**（背景/闲聊/重复自述，不是行为问题）→ 转给 `agent-config-tidy`，不属于本 skill

### 2. 冷审计——外科评估外包给全新上下文的子 agent

第 1 步的证据留主会话（摩擦来自当前会话，子 agent 没有这段记忆）；第 2 步的**文本审计**派
全新上下文的只读子 agent 执行：带着「我就是来改它的」心态看目标 SKILL.md，会顺着想改的
方向找证据；冷子 agent 只看文本本身，授权检查和 no-op 判定更硬。

用 Agent 工具发起**一次**审计，prompt 必须自包含：

- 目标 SKILL.md 绝对路径 + 摩擦证据（第 1 步找到的一手片段：它实际做了什么、期望是什么）；
- 指令：重读目标 SKILL.md 全文后回答审计问题清单——
  1. 误行为是否被现有文本授权？授权词在哪几行？
  2. 拟改方向是否是 no-op（现有规则未授权该行为，删不删都不变）？
  3. 最小修改建议（能删一句话解决吗？删词还是加禁令？）；
  4. 改动是否触碰 ±10 行边界、要不要拆多次迭代；
- 产出：逐问回答 + 行号引用，只评估不改文件，300 字以内。

主会话拿审计结论设计具体改法（第 3 步起照旧）。子 agent 不可用时明确报告并回退为主会话
自查，不要静默跳过。

### 3. 设计最小修改

（基于冷审计结论，主会话执行。）一次只改**一类行为**：

- 改动前重读目标 SKILL.md 全文（不要凭印象编辑）。
- 问：这个摩擦能否用**删一句话**解决？能删就不加。否定式禁令换正面表述。
- 需要新增时，仿照目标 skill 里已验证的句式，改动幅度控制在 **±10 行内**；超过就拆成多次迭代。
- **行为修改只动 SKILL.md**——它是唯一的行为事实源。

### 4. 变更记录

改完 SKILL.md 后，向用户**提议** commit（不主动执行 git）：

- 一句话说清**行为变化**（agent 会怎么不一样了），不要写「优化」「完善」这类不可检验的词。
- 建议信息格式：`skill-<name>: <行为变化>`，动机一句话放 body，可附摩擦来源。
- 用户同意才 commit；commit 由用户执行或用户明确授权后执行。
- 不需要 changeset 成册——个人仓库不对外发版，commit 一行即够。

### 5. 同步真相源（条件化）

修改生效需要 N 处一致，缺一处就是坏指针：

1. `skills/<分类>/<name>/SKILL.md`（行为事实源，必改）
2. `.claude-plugin/plugin.json` —— **仅新增/改名/删除 skill 时需要动**；改 description/正文不用
3. `README.md` 对应条目 —— **行为变化影响使用者理解时才更新**，纯内文小修可跳过

仓库外的已安装副本与 symlink：

4. `~/.agents/skills/<name>/`（运行时的**第二个独立副本**）→ `~/.codebuddy/skills/`、`~/.claude/skills/`（symlink 自动生效，无需操作；workbuddy 等复制式安装见 `sync-workbuddy`）

注意：本仓库 `skills/` 目录与 `~/.agents/skills/` 是两个**独立目录**（同内容不同文件）。改完仓库后，已安装的副本不会自动更新——需要把改动同步到 `~/.agents/skills/<name>/`（复制 SKILL.md，或重跑安装脚本）；codebuddy/claude 的 symlink 指向 `~/.agents/skills/`，只要后者更新就自动生效。

## 护栏

- 先证据、后修改：没有一手摩擦证据，只向用户要实例，不猜失败模式。
- 一次一类行为：±10 行，超限拆多次迭代。
- 只提议 commit，不主动 git；用户同意才执行。
- 行为修改只动 SKILL.md，plugin.json/README 按条件走。
