# 只追加文档历史机制 · 约定详述（references/convention.md）

本文解释 `doc-append-log` 这套机制"是什么、为什么、怎么守"，供智能体在遵循前理解底层动机。全文不绑定任何具体项目。

## 1. 问题

项目文档常被反复改写：一份设计纪要今天写、下周被"修订"覆盖，半年后智能体再读时，已经拿不到当时真实写下的结论，也无法分辨"哪篇是当前事实、哪篇已被取代"。跨会话、跨同事、中途加入的项目尤其明显——你不一定知道文档放在 `docs/` 还是 `log/`，也不一定清楚某篇结论现在还作不作数。

## 2. 机制

- **只追加，不改写**：每篇历史/结论文档创建后不再修改内容，保留原貌。
- **日期前缀命名**：新文件叫 `YYYY-MM-DD_主题.md`，让目录天然按时间有序。
- **单一索引 `INDEX.md`**：一份时间线表格，每行指向一篇文档并标注状态。它是智能体阅读历史的唯一入口。
- **目录无关**：文档可能在 `docs/`、`log/`、`logs/`、或某个你中途加入的项目的 `docs/` 下。机制不假设固定路径，先定位再操作。

## 3. 状态标记

| 状态 | 含义 |
| --- | --- |
| `当前事实` | 最新且生效 |
| `当前参考` | 仍有效，但属于某专题沉淀 |
| `历史背景` | 已被取代，仅作溯源 |

## 4. 为什么这样设计

- **不改写原 md**：保留当时真实写下的结论，避免后续"修订"误导智能体；溯源靠原文。
- **索引 + 状态，而非纯文件名排序**：纯文件名排序无法表达"哪篇生效、哪篇被取代"；状态标记解决这一点。
- **轻量脚本固化操作**：约定只写在文档里容易被多次会话写歪；两个小脚本把"建索引 / 追加一行"变成命令，结构才稳定。
- **目录无关**：不同项目、不同同事的存放习惯不一致，机制必须能定位任意文档目录，而不是假设 `docs/`。

## 5. 阅读顺序（智能体）

1. 定位文档目录（用 `scripts/locate_docs.sh`，或用户明确给出路径）。
2. 读 `<目录>/INDEX.md`。
3. 按"状态"定位需关注的文档；`当前事实` 为最新且生效。
4. 按需精读对应 md；不回改其内容。

## 6. 维护操作（智能体）

- 首次启用：`bash scripts/init_index.sh <目录>`（已存在则跳过）。
- 每次变更新增：`bash scripts/append_entry.sh <目录> <主题> [状态] [摘要]`。
- 旧文档被取代：不要改写它，新建一篇新文档并在索引里把旧篇状态改为 `历史背景`。
