# wx-flow — 个人全任务流程驱动器

带用户走完一个代码任务的完整生命周期。AI 领路：每个阶段开始时宣布
「现在只做这一项」，阶段收口处给出结论/选项，**等用户点头才进下一阶段**。

默认用户身份（与 branch-management / worktree 一致）：
- 姓名：wangxin / 王鑫，initials：`wx`

---

## 阶段总览

```
1 需求澄清 → 2 隔离判断 → 3 开发 → 4 收尾验证 → 5 MR + 清理
 (取证?+grill)  (worktree?)   (干活)    (按类型分流)   (branch-mgmt)
```

每个阶段结束后输出一行状态条，例如：

```text
[阶段 2/5 隔离判断] 完成 → 结论：进 worktree .wt-fix-otel
→ 进入阶段 3？（回车/ok 继续，或指出问题）
```

---

## 阶段 1：需求澄清

### 1a. 前置取证探测（原则 + 高频词，两层判断）

**判断原则**：当任务是**解释 agent 过去发生了什么**（行为不符、状态异常）
而非**设计新行为**时，先取证、再澄清——证据是 grill 问题的前提，先问后查
会让整场 grill 空转。

**高频触发词示例**（辅助快速命中，不做穷举）：「为什么没 / 行为不对 /
好像不太对 / 没收到 / 没注册 / 没下载 / 装到哪了 / 没生效 / 对比两个会话 /
查会话 / 取证」。

**命中后动作**：AI 明确建议取证入口，用户确认后先取证、拿到证据再进
grill（证据从"问用户记忆"升级为"查库铁证"）。入口按任务特征路由：

- agent 行为/注入/安装类疑案 → `/dp-session-forensics`（本地会话库）
- 云端专家任务 → `/dp-session-forensics-cloud`
- 不确定哪个入口 → `/ask-dp` 路由裁决
- 环境状态存疑 → `/dp-dev-bootstrap`（preflight 体检）

用户说不用取证就直接跳过，进 1b。

### 1b. grill 澄清

引导用户走 grill 类技能把需求磨清（用户手动拍板用哪个）：

- `/grill-one` — 纯问答澄清
- `/grill-one-with-docs` — 澄清 + 随手沉淀 GLOSSARY/CONTEXT/ADR

本技能只负责把门：**grill 过程中必须覆盖一个问题——**

> 「这个任务会和当前工作区的在制改动 / 其他 agent 会话撞车吗？」
> （在制改动是什么、别的会话在改什么文件、和本任务文件有无交集）

答案直接喂给阶段 2 的裁决。需求澄清完成、用户确认目标后，进阶段 2。

---

## 阶段 2：隔离判断（硬裁决）

先盘点现状（只读，直接执行）：

```bash
git status --short          # 工作区脏不脏、改了哪些文件
git branch --show-current   # 当前分支
git worktree list           # 已有哪些 worktree
```

并行会话检测：问用户「是否有别的 agent 会话在同一个仓库工作」，结合
阶段 1 的撞车答案。

**裁决条件（写死，AI 按此给结论，用户可否决）：**

满足任一条 → **必须进 worktree**（调用 `/worktree` 场景 1）：
1. 工作区有未提交改动，且与本任务的文件可能交集
2. 有其他 agent 会话正在同一工作区干活
3. 用户明确要并行开工

全部不满足 → **留在主仓库**，直接开发。

AI 必须先报盘点结果（脏文件清单 / 并行会话有无），再给结论和理由。
用户否决时按用户的来，但要在收尾报告里记录「用户选择不隔离」。

选定后向用户确认，进阶段 3。

---

## 阶段 3：开发

正常开发，无固定脚本。约定三点：

1. 用了 worktree 就在 worktree 目录里干活，`git rev-parse --show-toplevel`
   随时确认位置，别和主仓库混淆。
2. 中途需要其他技能（tdd、diagnosing-bugs、verify-run 等）随意叠加，
   本技能不拦。
3. 改动是 agent 的行为载体（agent md / 规则模板 / SKILL.md 等）时，
   动手前先走 `/agent-tdd` 写行为案例跑红——它是先行轨，收尾才补跑
   会破坏红绿次序。
4. 开发完成、自测通过后，向用户报「改动清单 + 涉及文件」，确认后进阶段 4。

---

## 阶段 4：收尾验证（按改动类型分流提示）

AI 按本次改动类型给出**提示与推荐**，选择权在用户：

| 改动类型 | 提示 | 推荐 |
|---|---|---|
| 纯文档 / 注释 / 配置微调 | AI 自查 + 附证据（diff 复述）即可；**改动含配置文档（SKILL.md / AGENTS.md / agent yaml）时可叠加 `/agent-config-lint <目录>` 自动检查** | 直接进阶段 5 |
| agent 行为载体（agent md / 规则模板 / SKILL.md 等改变 agent 行为的文案） | 走 `/agent-tdd`：阶段 3 已跑红的案例现在跑绿；护栏轨改动跑两轮 diff 验证无退步 | 推荐走 |
| 代码逻辑改动 | 走 `/closed-loop` 体检（差距清单 + 曳光弹证据） | 推荐走 |
| 有可执行验证物（测试/脚本/构建） | 可叠加 `/verify-run` 自动执行 | 锦上添花 |
| 涉及共享状态（push/发版/部署） | `/closed-loop` 判「大事」，必须用户确认 | 强烈推荐 |

用户说「跳过」也可以，AI 记录「用户选择跳过验证」进收尾报告。

---

## 阶段 5：MR + 清理（固定衔接，不现场发挥）

**没用 worktree 的**：按 `/branch-management` 收尾——提交、push 前确认、
开 MR（target 按仓库约定，默认 dev/develop）、MR 前检查。

**用了 worktree 的**：按 `/worktree` 场景 3 收尾——验证已合并
（`merge-base --is-ancestor`）→ 列删除清单（worktree 目录 / 本地分支 /
远端分支）→ **用户确认后**才执行删除 → `fetch --prune`。

push、删分支、开 MR 全部先征得用户确认（两个被衔接技能里已写死，
本技能不重复、不放松）。

全部完成后输出**收尾报告**：

- 五个阶段各自的结论（含用户否决/跳过的记录）
- 产物：分支 / MR / worktree 去向
- 遗留事项：没做的事、需要用户手动做的（如通知同事、发版）

---

## 红线

- 阶段收口处不许自作主张进下一阶段——等用户拍板
- 阶段 2 的裁决条件不许跳过盘点直接下结论
- 删除、push、force 类动作一律用户确认（衔接技能已有，此处重申）
- 中断后恢复：`git worktree list` + `git status` 盘点现场，从上次
  停下的阶段继续，不重头再来
